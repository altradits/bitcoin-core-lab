# 16.1 Interpreter reading drill — `C-SCRIPT-1`, `C-SCRIPT-2`

Tools allowed: `grep -n`, `less`, your editor, paper. No AI summaries, no blog posts.
Write all answers in `my-work/16-script-taproot-and-libsecp256k1/16.1-answers.md`. Record each search command you typed in `my-work/16-script-taproot-and-libsecp256k1/journal.md`.

## Part A — Find the entry points (30 min)

1. Find the line numbers (in *your* checkout) of `VerifyScript`, both `EvalScript` overloads,
   `VerifyWitnessProgram`, `ExecuteWitnessScript`, `SignatureHash`, `SignatureHashSchnorr` in
   `src/script/interpreter.cpp`. Which of them are `static`? Why does that matter for a reviewer
   (who can call them)?
2. Find every caller of `VerifyScript` in `src/` (exclude tests first, then include them). How many
   are in `validation.cpp`? Which class wraps the call for parallel block validation?

<details><summary>Hint 1</summary>A function defined <code>static</code> in a .cpp has internal linkage. Script checks for blocks are queued and run on worker threads.</details>
<details><summary>Hint 2</summary>Search for <code>VerifyScript(</code> and for <code>class CScriptCheck</code>. Then look for <code>operator()</code>.</details>

## Part B — Trace a P2WPKH spend (60 min)

Pretend you are the CPU. Input: scriptSig empty, scriptPubKey `OP_0 <20 bytes>`, witness `[sig, pubkey]`,
flags = `STANDARD_SCRIPT_VERIFY_FLAGS`.

Write, step by step, which function runs and which `if` branch is taken, until `set_success`.
For every branch name the flag that guards it. You must reach the line that builds the implicit
P2PKH script. Write it out in opcodes.

<details><summary>Hint 1</summary>The empty scriptSig still goes through <code>EvalScript</code> once. Then the scriptPubKey.</details>
<details><summary>Hint 2</summary><code>scriptPubKey.IsWitnessProgram(witnessversion, witnessprogram)</code> is the switch point.</details>

## Part C — Trace a taproot script-path spend (60–90 min)

Witness: `[sig, script, control_block]`, no annex. Write the sequence of checks inside the
`witversion == 1` branch of `VerifyWitnessProgram` and inside `ExecuteWitnessScript`. For each:
the error code returned when it fails (e.g. `SCRIPT_ERR_TAPROOT_WRONG_CONTROL_SIZE`).

Then answer:
- Where is `m_validation_weight_left` initialised and to what?
- What does `ExecuteWitnessScript` do *before* running a single opcode in tapscript?
- What happens to an unknown leaf version under consensus, and under standard flags?

## Part D — The flag table (45 min)

Build this table from `src/script/interpreter.h`, `src/policy/policy.h` and `GetBlockScriptFlags`
in `src/validation.cpp`:

| Flag | Bit | Consensus (in MANDATORY)? | Policy only? | Activated how (height/deployment/always)? | BIP |
|------|-----|---------------------------|--------------|-------------------------------------------|-----|

Fill **every** row from `SCRIPT_VERIFY_P2SH` to `SCRIPT_VERIFY_DISCOURAGE_UPGRADABLE_PUBKEYTYPE`.
Then write 5–8 sentences in your own words: *why does a soft fork need a flag, and why are the
`DISCOURAGE_*` flags policy-only?*

<details><summary>Hint 1</summary>Read the block comment above each enum value in <code>interpreter.h</code>; it usually names the BIP.</details>
<details><summary>Hint 2</summary><code>script_flag_exceptions</code> in <code>src/kernel/chainparams.cpp</code> explains the "always on except two blocks" rule.</details>
