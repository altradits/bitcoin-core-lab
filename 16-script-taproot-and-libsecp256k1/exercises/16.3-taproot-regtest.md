# 16.3 Build a taproot output with a script path and spend it both ways — `C-SCRIPT-4`

**Goal:** two wallets, Alice and Bob, share one taproot descriptor
`tr(<Alice key>, pk(<Bob key>))`. Alice holds the **internal key** private key → she can spend by
the **key path**. Bob holds only the **leaf key** private key → he must spend by the **script path**.
You will create both spends with PSBTs, confirm them, and explain every witness byte.

Binaries: `/Users/mac/bitcoin/build/bin/bitcoind` and `bitcoin-cli` (v29.0, already built).
Use a fresh datadir such as `$HOME/.bitcoin-lab16` so you do not disturb other stages.
**One `bitcoind` only.** Run `./lab.sh rest` first.

Record every command you type, and its important output, in `my-work/16-script-taproot-and-libsecp256k1/journal.md`.

---

## Step 1 — Start a regtest node you can query by txid

Start `bitcoind` in regtest, as a daemon, with your new datadir, with a transaction index, and
with fallback fees so the wallet can fund transactions. Then confirm with `getblockchaininfo` that
the chain is `regtest`.

<details><summary>Hint 1</summary>The checker uses <code>getrawtransaction &lt;txid&gt; 2</code>. Which startup option lets that work for confirmed transactions that are not in your wallet?</details>
<details><summary>Hint 2</summary><code>bitcoind -help</code> and search for <code>txindex</code>, <code>fallbackfee</code>, <code>datadir</code>, <code>daemon</code>, <code>regtest</code>.</details>

Make yourself a shell alias or variable for the long `bitcoin-cli ... -datadir=...` prefix — and
type it yourself. You will need it ~40 times. Export the same string as `BITCOIN_CLI` for the checker.

## Step 2 — Three wallets

Create `miner`, `alice` and `bob` descriptor wallets. Mine enough blocks to `miner` that its
coinbase is spendable.

<details><summary>Hint 1</summary>Coinbase maturity is 100 blocks (Stage 01).</details>

## Step 3 — Get the keys you need

From **alice**, get her taproot (BIP86) descriptor *with* private keys, and *without*.
From **bob**, the same. You want the account-level extended keys with their origin info
(the part that looks like `[fingerprint/86h/1h/0h]tprv...` / `tpub...`).

<details><summary>Hint 1</summary>One RPC lists a wallet's descriptors; a boolean argument shows private keys. Look for the one that starts with <code>tr(</code> and is <em>not</em> internal (change).</details>
<details><summary>Hint 2</summary><code>bitcoin-cli -rpcwallet=alice help listdescriptors</code>. Copy only the key expression between <code>tr(</code> and <code>/0/*</code>.</details>

Write down, in your journal: Alice's tprv, Alice's tpub, Bob's tprv, Bob's tpub. Never reuse
these outside regtest.

## Step 4 — Write the two descriptors yourself

Use a fresh derivation branch (for example `/7/*`) so these addresses do not collide with the
wallets' own.

- For **alice**: internal key = her **private** key, leaf `pk(...)` = Bob's **public** key.
- For **bob**: internal key = Alice's **public** key, leaf `pk(...)` = his **private** key.

Get each descriptor's checksum, then compare: do both *public* forms have the same checksum?
They must describe the same outputs.

<details><summary>Hint 1</summary>Read <code>doc/descriptors.md</code> in <code>/Users/mac/bitcoin</code>: search for <code>tr(</code>.</details>
<details><summary>Hint 2</summary><code>getdescriptorinfo</code> gives you the checksum and the public form.</details>

## Step 5 — Import and derive

Import the right descriptor into each wallet (not active, ranged `[0,10]`, timestamp `now`).
Then derive the first two addresses from the **public** descriptor with a node-level RPC
(no wallet). Check that `alice` and `bob` both say `ismine: true` for those addresses.

<details><summary>Hint 1</summary><code>importdescriptors</code> takes a JSON array of objects. Watch your shell quoting — use single quotes around the JSON.</details>
<details><summary>Hint 2</summary><code>deriveaddresses</code> and <code>getaddressinfo</code>.</details>

Questions for your journal: what does a P2TR address start with on regtest? How long is the
scriptPubKey hex, and what are its first two bytes?

## Step 6 — Fund both addresses

From `miner`, send 1 BTC to address index 0 and 1 BTC to address index 1. Mine one block.
Record both outpoints (txid:vout).

## Step 7 — Key-path spend (Alice)

In **alice**: create a funded PSBT that spends **only** the index-0 outpoint (no other inputs) to a
`miner` address, at a fixed fee rate you choose. Process it in `alice`, finalize it, broadcast it.
Do not mine yet. Decode the final transaction and look at the witness of the input.

<details><summary>Hint 1</summary><code>walletcreatefundedpsbt</code> accepts explicit inputs and an option that stops it adding more.</details>
<details><summary>Hint 2</summary>Then <code>walletprocesspsbt</code>, <code>finalizepsbt</code>, <code>sendrawtransaction</code>. Use <code>decodepsbt</code> between steps to watch <code>taproot_key_path_sig</code> appear.</details>

## Step 8 — Script-path spend (Bob)

Same as Step 7, but in **bob** and with the index-1 outpoint. Before finalizing, decode the PSBT:
which taproot fields did Bob's wallet fill in (`taproot_script_path_sigs`, `taproot_scripts`,
`taproot_bip32_derivs`...)? Why is there no key-path signature?

Mine one block. Now run the checker with both txids.

## Step 9 — Explain every witness element (the real learning)

For Bob's tx, in your journal:
1. Element 0: what is it, and how long? Is there a sighash byte appended? Why/why not?
2. Element 1: decode the script (`decodescript`). Which opcodes? Which key?
3. Element 2 (control block): split it into leaf-version/parity byte, internal key, merkle path.
   Is the internal key Alice's derived x-only key? What is the parity bit and what does it mean?
4. Using **your** `tagged_hash.py` from 16.4: compute the tapleaf hash of element 1 and the tweak
   from the internal key and that leaf hash (single leaf → merkle root = leaf hash). Show that
   this matches the output key in the scriptPubKey you spent. (You need EC point addition for the
   very last step; it is enough to show the tweak — or do the point maths in Python as a stretch.)
5. Compare vsize of Alice's and Bob's transactions. Which is cheaper and why? What does this say
   about putting the most likely spending condition in the key path?
