# SPOILER — Stage 07 quiz answers

1. Errors most likely in hand-copied descriptors (hex, key paths) then change only the low 5 bits of a symbol, which BCH codes detect best. Case errors move a character exactly 32 positions (a different group, same low bits), so they also affect a single symbol. See the comment above `INPUT_CHARSET` in `src/script/descriptor.cpp`.
2. `0h` = 0x80000000 = 2147483648. `2147483647h` = 0xFFFFFFFF. `2147483648` unhardened would set bit 31, so it could not be told apart from `0h`. `ParseKeyPathNum` rejects anything > 0x7FFFFFFF.
3. Signatures are collected in the input maps (partial sigs) and placed into the tx only by the Finalizer. A filled scriptSig would mean the creator already put data there, and the txid would be ambiguous. Witness serialization is not allowed: a "witness" in the unsigned tx is meaningless, and a 0-input tx would be ambiguous with the segwit marker. Core reads it with `TX_NO_WITNESS`.
4. `analyzepsbt` actually tries to sign and finalize. If the input has all the signatures it needs, the answer is `finalizer`. If more are needed (e.g. 1 of 2 in a 2-of-2), it is `signer`. If other data is missing, it is `updater`. `NextRole` only counts signatures, so it says `finalizer` for the 1-of-2 case. Core says `signer`.
5. `combinepsbt` is the Combiner: it merges PSBTs of the **same** unsigned tx (`PartiallySignedTransaction::Merge`). `joinpsbts` builds a **new** tx out of the inputs and outputs of several different PSBTs, which is a Creator-like action.
6. A signature commits to the amount spent (BIP143 / BIP341). Without the UTXO, a malicious host could lie about input amounts and trick the signer into paying a huge fee. For segwit v0 the full previous tx is still preferred, because of the 2020 "fee attack" with two inputs. Search "non_witness_utxo" in `src/psbt.cpp`, and read bip-0174's notes.
7. `v:` appends `OP_VERIFY` (or uses the VERIFY form, e.g. `OP_CHECKSIGVERIFY`), so the fragment leaves nothing on the stack. `older(144)` becomes `<144> OP_CHECKSEQUENCEVERIFY`, and the spending input's `nSequence` must encode 144 blocks (BIP68/BIP112).
8. Two parsers could disagree about which value is "real". A hardware wallet shown one UTXO amount while the host uses another is the classic case. BIP174 requires rejecting duplicates, and Core throws `Duplicate Key, …`.
