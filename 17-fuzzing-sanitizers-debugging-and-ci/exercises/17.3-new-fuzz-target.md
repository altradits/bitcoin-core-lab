# 17.3 Write a NEW fuzz target: `taproot_merkle` — `C-FUZZ-2`, `C-FUZZ-3`

There is no fuzz target that calls `ComputeTapbranchHash` or `ComputeTaprootMerkleRoot` directly
(you checked in 17.1 Q7 — re-check on the latest master before you invest time). These functions
are small, pure, and consensus-critical: an ideal first harness.

Work in your worktree `/Users/mac/bitcoin-fuzz` on your topic branch.

## Part A — Design on paper first (30 min)

In `my-work/17-fuzzing-sanitizers-debugging-and-ci/17.3-design.md` answer:
1. What are the inputs of each of the three functions, and what are their preconditions? (Read the
   `assert`s at the top of `ComputeTaprootMerkleRoot`.)
2. Three invariants that must hold for **all** inputs (the skeleton lists them — explain *why* each
   holds by pointing at lines of `interpreter.cpp`).
3. How will you keep inputs bounded? (Script length, number of path nodes.)

## Part B — Write it (90 min)

1. Copy `exercises/taproot_merkle_skeleton.cpp` to `src/test/fuzz/taproot_merkle.cpp` in the worktree.
2. Replace every TODO. Use only helpers that exist in `src/test/fuzz/util.h` (grep them).
3. Add the file to `src/test/fuzz/CMakeLists.txt` in alphabetical order.
4. Run the checker's static part: `python3 17-fuzzing-sanitizers-debugging-and-ci/check_fuzz_target.py`.

<details><summary>Hint 1</summary>For "fold by hand", copy the loop structure of <code>ComputeTaprootMerkleRoot</code> but feed it your own vector of nodes.</details>
<details><summary>Hint 2</summary><code>ConsumeIntegralInRange&lt;size_t&gt;(0, TAPROOT_CONTROL_MAX_NODE_COUNT)</code> gives you k; <code>ConsumeFixedLengthByteVector</code> gives you 32 bytes.</details>

## Part C — Build and run (30 min + incremental build)

1. Rebuild `build_fuzz_mac` (-j3). ccache makes this an incremental build.
2. Confirm your target appears in the target list.
3. Create `my-work/17-fuzzing-sanitizers-debugging-and-ci/taproot_merkle_corpus/` with 5–10 input files you make yourself (empty
   file, a few random byte files from `head -c N /dev/urandom`, one very long one).
4. Run your target over that directory. Then run the full checker again (it now does the dynamic part).

## Part D — Mutation test + crash reproduction (45 min) — this is the important bit

1. **Temporarily** break `ComputeTapbranchHash` in the worktree so it no longer sorts its inputs
   (change one line). Do not commit this.
2. Rebuild. Run your target over your corpus. Does an `assert` fire? Which input file triggers it?
   (If none does, your corpus is too weak — make an input where the two 32-byte values differ.)
3. Reproduce the crash with **only** that single file as argument. Then run the same command under
   `lldb` and get a backtrace (`bt`). Paste the top 5 frames into your journal.
4. Restore the original line (`git diff` must show only your new harness + CMakeLists change),
   rebuild, and confirm the crash input now passes.

You just proved that your harness detects a real consensus bug class. That is the proof a
reviewer wants for a new harness.
