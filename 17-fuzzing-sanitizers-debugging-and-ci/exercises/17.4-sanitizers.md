# 17.4 Sanitizers — `C-DEBUG-2`

Goal: build `test_bitcoin` once with ASan+UBSan, trigger one report of each kind **on purpose** in
a throwaway branch, read the reports, and clean up. Journal: `my-work/17-fuzzing-sanitizers-debugging-and-ci/journal.md`.

**RAM:** sanitizer builds are the heaviest thing in this stage. Use `-j2`, build only the
`test_bitcoin` target, nothing else open.

## Part A — Read first (30 min)

1. In master `doc/developer-notes.md`, section "Sanitizers": which CMake variable, which example
   values, which env vars point at the suppression files?
2. Open `test/sanitizer_suppressions/ubsan`. Pick two suppressions and explain what they hide and
   why that might be acceptable.
3. Which sanitizers does each of these CI files enable (read the `SANITIZERS` value):
   `00_setup_env_native_asan.sh`, `00_setup_env_native_tsan.sh`, `00_setup_env_native_msan.sh`,
   `00_setup_env_native_fuzz.sh`? Which of them can you reproduce on macOS arm64? Which not, and why?

## Part B — Build (≈1–2 h wall clock, start it, then do Part A)

In your master worktree, configure a new build dir `build_asan` with ASan and UBSan (no wallet GUI,
no bench), and build only the `test_bitcoin` target with `-j2`.

<details><summary>Hint 1</summary><code>-DSANITIZERS=</code> takes a comma list; <code>cmake --build &lt;dir&gt; --target &lt;name&gt; -j2</code>.</details>

## Part C — Make it scream (45 min), on a throwaway branch

Create a branch `sanitizer-playground` (never push it). Write **one tiny new Boost test case** in an
existing test file of your choice that:
1. reads one element past the end of a `std::vector<int>` through a raw pointer → ASan report,
2. in a second test case, overflows a signed `int` (`INT_MAX + 1` computed at runtime from a
   variable) → UBSan report.

Rebuild `test_bitcoin` (incremental), run **only** your two cases with `--run_test=suite/case`.
For each report, annotate in your journal: error type, the access (READ/WRITE, size), the frame in
*your* code, the allocation site (ASan), and the UBSan "runtime error" line.

Then run one real suite, e.g. `script_tests`, under the same build and confirm it is clean.

## Part D — TSan reasoning (no build required)

Read the "Locking/mutex usage notes" in developer-notes. Explain in your own words what TSan
reports that `DEBUG_LOCKORDER` does not, and vice versa.

## Clean up
`git switch` back to your topic branch, delete `sanitizer-playground`. Keep `build_asan` only if
you have disk space.
