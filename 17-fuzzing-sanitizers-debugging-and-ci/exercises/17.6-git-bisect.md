# 17.6 git bisect drill — `C-GIT-5`

**Scenario.** A merchant running your 29.x node says: "after I upgraded to a master build, my
replacements suddenly need far less extra fee than before." The default incremental relay fee
(`-incrementalrelayfee`) changed somewhere between 29.x and master. Find the **first commit** on
master that changed it — using `git bisect`, not `git log -S` (you may use `log -S` afterwards to
double-check).

You will not compile anything: your "test" is a tiny script that inspects the source. In real life
the script would build and run one test; the mechanics are identical.

## Setup (do not disturb your 29.x checkout)

Bisect checks out many commits. Do it in a **separate worktree** (e.g. `/Users/mac/bitcoin-bisect`,
detached at master). Never bisect inside a tree that holds uncommitted work.

## Steps

1. Find the "good" commit: the point where 29.x branched from master
   (one git command finds the common ancestor of `HEAD` in `/Users/mac/bitcoin` and `master`).
   Confirm by reading `src/policy/policy.h` at that commit that the default is the old value.
2. "Bad" commit: `master`. Confirm the value differs there.
3. Write `my-work/17-fuzzing-sanitizers-debugging-and-ci/bisect_test.sh` yourself: exit **0** when the tree still has the old default,
   **1** when it does not. (Which exit code means "skip"? Write it in a comment.)
4. Start the bisect in the worktree, mark good/bad, and run your script automatically.
5. Write the first bad commit's **full** hash on line 1 of `my-work/17-fuzzing-sanitizers-debugging-and-ci/bisect-result.txt`.
6. `git bisect log` → save it to `my-work/17-fuzzing-sanitizers-debugging-and-ci/bisect-log.txt`. Then reset the bisect.
7. Run `python3 17-fuzzing-sanitizers-debugging-and-ci/check_bisect.py`.

<details><summary>Hint 1</summary><code>git merge-base</code>; <code>git show &lt;rev&gt;:&lt;path&gt;</code>; <code>git bisect start &lt;bad&gt; &lt;good&gt;</code>.</details>
<details><summary>Hint 2</summary><code>git bisect run &lt;script&gt;</code> runs it from the worktree root. <code>grep -q</code> returns 0/1 for you.</details>

## Then (the reviewer part)

1. How many steps did bisect take? Compare with log₂ of the number of commits in the range
   (`git rev-list --count good..bad`).
2. Read the commit message. Which PR merged it? (Find the merge commit whose second parent's
   history contains it: `git log --merges --ancestry-path <commit>..master | tail -1`.)
3. What else did that commit change at the same time? What would you, as a reviewer, check in
   `doc/policy/mempool-replacements.md` and release notes?
4. Stretch (compiles — only with ccache and a quiet machine): bisect a *test* instead of a grep,
   e.g. a functional test that asserts the old fee. Estimate time per step on your M1 first.
