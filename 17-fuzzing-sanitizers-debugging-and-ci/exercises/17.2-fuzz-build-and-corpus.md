# 17.2 Engine-less fuzz build on 8 GB + corpus replay — `C-FUZZ-1`, `C-FUZZ-3`

Goal: a **master** worktree, an engine-less fuzz binary built with Apple clang, and a few
`qa-assets` corpora replayed through it. Log every command in `my-work/17-fuzzing-sanitizers-debugging-and-ci/journal.md`.

Before you start: `./lab.sh rest`, close browsers, plug in power. Read the "8 GB M1 survival
rules" in the README again.

## Step 1 — A separate worktree on master (do not touch your 29.x checkout)

Create a new git worktree of `~/bitcoin` at `~/bitcoin-fuzz`, on a **new topic
branch** (for example `fuzz-taproot-merkle`) starting from `master`. Check with `git worktree list`.

<details><summary>Hint 1</summary><code>git -C ~/bitcoin worktree add -h</code>. The <code>-b</code> flag creates the branch.</details>
<details><summary>Hint 2</summary>Your local <code>master</code> may be behind upstream. Decide whether to <code>git fetch</code> first and write down which commit you built.</details>

## Step 2 — ccache

Install `ccache` with Homebrew. Find how Core's CMake decides to use it (option name in the
top-level `CMakeLists.txt`). After configuring, confirm in the CMake output that ccache was found.

## Step 3 — Configure

In the worktree, configure a build directory named `build_fuzz_mac` with:
- the option that builds only the fuzz binary,
- **no** `SANITIZERS` (Apple clang has no libFuzzer runtime),
- a `Debug` or `RelWithDebInfo` build type (choose, and justify in your journal — think about
  which you need for 17.3 crash debugging).

<details><summary>Hint 1</summary>Read <code>ci/test/00_setup_env_mac_native_fuzz.sh</code> on master. Your config can be a subset of its <code>BITCOIN_CONFIG</code>.</details>
<details><summary>Hint 2</summary><code>cmake -B &lt;dir&gt; -D&lt;OPTION&gt;=ON -DCMAKE_BUILD_TYPE=...</code></details>

Read the CMake summary it prints. Which targets are ON/OFF? Copy the summary into your journal.

## Step 4 — Build with a safe `-j`

Build with at most 3 jobs. Time it (`time ...`). While it runs, open Activity Monitor → Memory
and write down the peak "Memory Used" and the pressure colour. If it turns red, stop and use `-j2`.

## Step 5 — List and run a target

1. List all compiled targets (env var from 17.1). How many are there?
2. Run the `fee_rate` target on stdin with a handful of bytes you type (`printf ... |`). What does
   the binary print when the input is processed?

## Step 6 — A small slice of qa-assets

Do **not** clone the whole repository blindly. Make a partial, sparse clone of
`https://github.com/bitcoin-core/qa-assets` into `~/qa-assets`, then check out only the
`fuzz_corpora/` folders for 2–3 small targets (start with `fee_rate`, `script_flags`, `parse_script`).

<details><summary>Hint 1</summary><code>git clone --help</code>: look at <code>--filter=blob:none</code>, <code>--sparse</code>, <code>--depth</code>.</details>
<details><summary>Hint 2</summary><code>git sparse-checkout set &lt;dir&gt; &lt;dir&gt;</code>.</details>

Run each target over its corpus directory. Record how many inputs ran and how long it took.
Also run the same through the runner script your build dir contains under `test/fuzz/test_runner.py`
(read its `--help`; pass `--par 2` at most).

## Step 7 — Reproduce a crash from one file (practice)

You cannot get a real CI crash on demand, so make one safely in the next exercise (17.3, Part D).
For now, write in your journal the exact steps from master `doc/fuzzing.md` section
"Reproduce a fuzzer crash reported by the CI", in your own words, and why the qa-assets commit
must match.

## Done when
- Worktree + branch exist, build finished, targets listed, three corpora replayed, journal has
  timings and memory notes.
